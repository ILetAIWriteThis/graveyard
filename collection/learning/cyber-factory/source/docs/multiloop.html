The question this answers

Classifying one log line at a time cannot see an intrusion. An intrusion is a shape made of lines that are minutes and dozens of events apart: a port scan, then failed passwords, then one password that works, then sudo, then a new root account. Each line on its own is unremarkable. classify_logs.py looks at exactly one line and has no memory of the last one.

So multiloop.py hands the model the stream in batches and lets it decide when it has read enough. That decision is the whole experiment.

Batched delivery, whole context

Batching paces the conversation, not the model's sight. At the moment the verdict is written, the full stream is visible in a single prompt. The cost is quadratic: five batches means batch one is sent five times. That, and not comprehension, is what makes --batch-size 1 a bad idea, and what will eventually break this design on a stream of thousands of lines.

The loop

Why the gate exists

The system prompt tells the analyst to keep pulling batches until the stream runs out. It does not obey. Stated as a rule, qwen2.5:7b stopped at 10 of 40 lines; with the rule sharpened, it stopped at 20 of 40. Both times it missed a brute-force burst sitting in a batch it never asked for.

So an answer offered while lines are still unseen is not returned to the caller at all. A plain user message goes back into the same conversation, and the loop runs another turn. The rejected answer stays in the transcript, so the model sees its own premature call with the correction directly after it.

step 0request_more_logs() → lines 14–27, 42 still unseen
step 1early verdict rejected, 42 line(s) unseen → NUDGE
step 2request_more_logs() → lines 28–41, 28 still unseen
step 3early verdict rejected, 28 line(s) unseen → NUDGE
step 4request_more_logs() → lines 42–55, 14 still unseen
step 5early verdict rejected, 14 line(s) unseen → NUDGE
step 6request_more_logs() → lines 56–69, 0 still unseen
step 7verdict accepted — 70/70 lines seen

Three rejections in one run. Left alone, this model would have called the incident after 14 lines, before the successful login, the privilege escalation, or the beacon had happened. --allow-early-verdict turns the gate off if you want to watch it fail; --max-steps bounds the whole thing either way.

What it was reading

STAGE 1Recon

Four blocked SYNs from one external IP across 22, 80, 8080, 8443.

STAGE 2Brute force

Seven failed passwords for test from that same IP.

STAGE 3Foothold

One accepted password. Same user, same IP, two lines long.

STAGE 4Privilege escalation

sudo /bin/bash, root session opened for test.

STAGE 5Persistence

New UID 0 account svc-backup, cron replaced, service installed.

STAGE 6C2 beacon

Repeated curl | bash to the attacker IP, outbound allowed.

The stages share one attacker IP, and everything after the foothold shares one compromised account. That shared identity is the only thread connecting them. The decoy spray exists to punish pattern-matching on volume: it is louder than the real intrusion and completely unrelated to it.

What each model got wrong

analyst · qwen2.5:7b incident · critical

Called a brute force followed by successful SSH and script execution. Right shape, wrong actor: its lead evidence is the decoy IP, and it never connects the accepted password to the seven failures immediately before it.

  • Missed privilege escalation entirely.
  • Missed the UID 0 backdoor account.
  • Cited the loud decoy over the real chain.
verifier · llama3.1:8b 2/5 disagree

Correctly flagged the actor confusion, then argued the accepted password was "a legitimate login" and that repeated curl | bash as root shows no malicious intent. It also listed a GNOME backend warning as a missed signal.

Two models of this size produce two opinions, not a ground truth. The verifier is worth keeping because it catches the analyst inventing coordination between unrelated IPs, which it did on both runs. It is not worth trusting on whether root running curl | bash from cron is fine.

The obvious next move is an answer key: the scenario already knows which lines it emitted and what each stage was, so a verdict could be scored against what actually happened instead of against another model's opinion.

Run it

uv run synthetic-logs/generate_syslog.py -n 70 --scenario ssh_intrusion \
    --format jsonl -o /tmp/chain.jsonl

uv run local-agent/multiloop.py /tmp/chain.jsonl --format jsonl \
    --batch-size 14 --verbose -o /tmp/chain_run.json

The analyst needs a tool-calling model, which rules out gemma3 at any size in Ollama. The verifier only needs structured output. --output writes a reconstructable JSON artifact containing the input and shown logs, prompts and settings, full analyst transcript, loop and tool events, extraction exchange, verifier exchange, and final results.
